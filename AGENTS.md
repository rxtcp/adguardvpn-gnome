# Repository instructions for AI agents

These instructions apply to the entire repository. Read any more specific
`AGENTS.md` in a directory before changing files there. Follow the user's task
and applicable higher-priority instructions; preserve unrelated working changes.

## Read before editing

- [README.md](README.md): user installation, optional helper and uninstallation.
- [docs/development.md](docs/development.md): architecture, tests and desktop checks.
- [docs/behavior-contract.md](docs/behavior-contract.md): behavior to preserve during refactoring.
- [docs/privileged-helper.md](docs/privileged-helper.md): read before changing the helper, Polkit or privileged scripts.
- [docs/site-routing.md](docs/site-routing.md) and [docs/site-routing-acceptance.md](docs/site-routing-acceptance.md): read before changing routing, DNS, migration or the new system service.

Inspect the relevant implementation and tests before editing. Work from the
current target branch; check whether an earlier PR was merged before reusing
its branch. Make each change serve the requested task.

## Test-driven changes

1. For refactoring, record any previously untested behavior in characterization
   tests and confirm they pass against the original implementation first.
2. For a bug fix or new behavior, write a regression or acceptance test first.
   Run it and confirm it fails for the expected reason before implementing the
   change. Rebuild TypeScript before testing changed extension code.
3. Make the smallest change that passes the test, then refactor while keeping
   the relevant tests green. Preserve the behavior contract unless the task
   deliberately changes behavior; document intended changes to that contract.
4. Test observable state, command arguments, persistence and failure handling.
   Use deterministic clocks, deferred subprocess completion, temporary paths
   and the existing GNOME test environment. Avoid tests that merely repeat the
   implementation or assert private structure.

Cover normal, error and boundary cases, including cancellation, timeouts,
concurrent operations and late completion after shutdown when relevant. Keep
fixtures synthetic and independent of an installed VPN or desktop session.

## Types, names and module boundaries

- Write extension runtime code in TypeScript and preserve the strict compiler
  settings in `tsconfig.json`. Validate external values as `unknown`; avoid
  `any`, suppression comments and unjustified non-null assertions or casts.
- Use descriptive English names that explain the domain and responsibility.
  Prefer established terms such as CLI and ISO country code over invented
  abbreviations. Follow the surrounding naming and formatting conventions.
- Give each module one cohesive responsibility. Split code when unrelated
  responsibilities accumulate; file size follows its task, without an
  arbitrary line-count limit or unnecessary tiny wrappers.
- Keep domain parsing and models in `src/domain/` free of GNOME and I/O imports.
  Put Gio/GLib I/O in `src/platform/`, connection/status/catalog orchestration
  in `src/application/`, and widgets and navigation in `src/ui/`.
- Keep `src/extension.ts` focused on enable/disable and panel integration.
  Clean up timers, cancellation handlers and UI resources during shutdown.
- Keep `src/prefs.ts` as the separate standard preferences entry. Site Routing
  domain, platform, application and UI modules follow the same layer boundaries.
- Keep the privileged controller in Python and self-contained unless the task
  explicitly requires redesigning its installation and trust boundary.
- Use `.js` suffixes for relative runtime imports in TypeScript and `import type`
  for types. Preserve GJS `gi://` and `resource:///` imports. Node.js and npm
  packages are build/test tools, not extension runtime dependencies.
- Edit sources in `src/` and assets in `extension/`; `dist/` is generated by
  `npm run build`. Do not commit generated output or edit it as the source fix.
  Update lockfiles with dependency changes and keep the installed ZIP complete.

## Privileged operations and user data

- Server browsing and latency measurement use the unprivileged CLI. Only the
  existing connection/disconnection/status allowlist reaches the helper.
- Preserve fixed executable paths, the controlled environment, validated
  argument arrays, root ownership and ancestor permission checks. Never turn
  user input into shell source or run a user-writable CLI/script as root.
- Preserve signature verification, the separate private root profile, atomic
  selection writes and serialized mutations. Keep Polkit scoped to the intended
  active local user; do not add broad sudoers or generic systemd permissions.
- Preserve current-invocation journal status checks and the systemd disconnect
  fallback. Starting a process alone does not confirm an established VPN.
- Use mocks and temporary directories for routine verification. Running real
  install/uninstall/login commands, requesting root privileges or changing host
  VPN, routing, DNS, Polkit or systemd state requires an explicit request for
  that live operation. Isolated installer tests with fake commands are allowed.
- Do not commit credentials, login profiles, keys, machine logs, real corporate
  routes or the proprietary AdGuard executable. Keep existing user and corporate
  VPN configuration outside the scope of ordinary extension changes.
- Site Routing changes require their separate interactive Polkit action.
  Preserve guard-before-allow, stable identities, exact owned cleanup, private
  write-ahead state and explicit known-IP limits. Never silently release a
  known IP on DNS/provider failure. Reject unverified IPv6 and ambiguous paths.
- NM migration must show the exact diff and retain a verified non-secret backup.
  Protect, retire and rollback are distinct authorized changes. Matching only
  an address is insufficient permission to delete a foreign route/rule.

## Verification commands

For a fresh checkout, use Node.js 22.18 or newer and install the development
dependencies. Use the system Python with native Gio/GLib bindings installed
(`python3-gobject` on Fedora or `python3-gi` on Ubuntu):

```bash
npm ci
python3 -m venv --system-site-packages .tmp/python-env
.tmp/python-env/bin/python -m pip install -r requirements-dev.txt
```

For a focused extension test during development:

```bash
npm run build
node --experimental-vm-modules --test tests/extension/behavior.test.mjs
```

For changes to executable code, run the relevant focused tests and the complete
checks below before reporting completion. Run these sequentially: the extension
and Python archive checks both rebuild `dist/`.

```bash
npm run typecheck
npm run test:coverage
PYTHONDONTWRITEBYTECODE=1 .tmp/python-env/bin/python -m coverage run -m unittest discover -s tests -v
.tmp/python-env/bin/python -m coverage report
for script in scripts/*.sh helper/client.sh; do
    bash -n "$script" || exit 1
done
python3 - <<'PY'
from pathlib import Path
import xml.etree.ElementTree as ET
for path in [*Path('helper').glob('*.policy'), *Path('routing_system').glob('*.policy'), *Path('routing_system').glob('org*.conf')]:
    ET.parse(path)
PY
```

Maintain 100% line, branch and function coverage of the compiled extension and
100% statement and branch coverage of `helper`, `site_routing` and
`routing_system`, as enforced by CI. Native variants use a fake connection;
unit tests must not contact the host system bus. Use the isolated namespace CI
job for real `ip`/`nft` testing; never run its entry in the host namespace.
Do not lower thresholds, hide executable code from coverage or replace failing
assertions with skips to make a change pass. For documentation-only changes,
validate links, referenced paths, command syntax and `git diff --check`; new
runtime tests are not required.

## Documentation and delivery

- Keep code identifiers, comments, UI text and repository documentation in
  English unless the task requests localization. Reply in the user's language.
- Changes to installation, privileges, service behavior or stored data must
  update the end-to-end installation and removal instructions in the main
  README, including retained data and optional cleanup. Keep the detailed
  helper and development documentation consistent with the scripts.
- Use a task branch and a focused PR for repository changes. Do not merge PRs,
  publish releases or rewrite published history without a request to do so.
- Describe the resulting behavior, validation performed and material remaining
  limitations. Report failed or unavailable checks honestly. Mocked tests do
  not establish live GNOME, Polkit, TUN, routing or DNS compatibility; distinguish
  automated results from an actual desktop smoke test.
- Site Routing stays experimental until the documented Fedora acceptance run
  passes, particularly AC-03/04/06/11. Unit coverage and network namespaces do
  not prove AdGuard TUN/AUTO coexistence or early boot protection.
