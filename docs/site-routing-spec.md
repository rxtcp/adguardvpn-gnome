# Site Routing для adguardvpn-gnome — техническое задание v1.0

**Статус:** согласовано по функциональному объёму; готово к декомпозиции и реализации.  
**Дата:** 2026-11-23.  
**Проект:** [rxtcp/adguardvpn-gnome](https://github.com/rxtcp/adguardvpn-gnome).  
**Целевая платформа первой версии:** Fedora Workstation, GNOME Shell, NetworkManager, AdGuard VPN CLI через существующий защищённый helper.

> Этот документ предназначен в том числе для публичного репозитория. Реальные корпоративные домены, IP-адреса, UUID, ключи, учётные данные и маршруты пользователя здесь не приводятся.

## 1. Цель и границы

Добавить в GNOME-расширение **Site Routing** — интерфейс, позволяющий пользователю назначать **точному доменному имени** одно из доступных подключений:

- VPN, управляемый NetworkManager (включая OpenVPN и WireGuard);
- AdGuard VPN CLI из защищённого профиля `adguardvpn-gnome`;
- прямое физическое интернет-подключение (`direct`).

Для создания, изменения и удаления правил пользователь не должен вручную выполнять `nmcli`, `ip route`, `ip rule` или команды AdGuard CLI. После однократного подтверждения изменения через Polkit дальнейшее применение сохранённого правила при переподключениях осуществляется автоматически.

**Главная семантика:** если выбранное подключение недоступно, соответствующий трафик **блокируется**, не переключается на другой VPN, на прямое подключение или на системный маршрут по умолчанию. Автоматическое подключение отключённого VPN не выполняется.

### 1.1. Согласованные решения

| Тема | Решение для v1 |
| --- | --- |
| Механизм | DNS/IP-маршрутизация с проверками и явными ограничениями |
| Изменение системных правил | Подтверждение через Polkit; автоматическое восстановление без повторного запроса |
| Поддомены | Только точные FQDN; wildcard и суффиксные правила не поддерживаются |
| Источники подключений | Fedora + NetworkManager + защищённый AdGuard VPN CLI |
| Отключённый целевой VPN | Блокировать, без fallback и без автоматического подключения |
| Неохваченные домены | Не изменять существующую системную маршрутизацию |

### 1.2. Гарантии и ограничения

Это **IP-ориентированная реализация**, а не прозрачный прикладной прокси. Она управляет адресами A/AAAA, которые смог разрешить и отследить контроллер. Нельзя обещать абсолютную доменную изоляцию при самостоятельном DNS-over-HTTPS приложения, неизвестных кэшированных адресах, общих IP у разных доменов или изменениях DNS до очередной синхронизации.

Термин **«блокировка без fallback»** в v1 означает: для **известных контроллеру IP-адресов** домена установлено правило, которое при недоступности целевого подключения предотвращает использование другого маршрута. Интерфейс и документация обязаны показывать эту границу гарантии; нельзя маркировать её как защиту от любых утечек. Для более строгой доменной гарантии потребовался бы отдельный DNS/прокси-слой — он не входит в v1.

## 2. Сценарии пользователя

1. Пользователь открывает **Настройки → Site Routing**.
2. Вводит `https://packages.corp.example/repository/path`.
3. Приложение показывает нормализованный домен `packages.corp.example` и доступные подключения.
4. Пользователь выбирает конкретный VPN и подтверждает создание правила через Polkit.
5. Контроллер сохраняет домен, определяет текущие A/AAAA, устанавливает блокирующую защиту и рабочий маршрут через выбранный VPN.
6. Пользователь видит состояние правила и диагностические данные без необходимости открывать терминал.
7. При исчезновении туннеля маршрут не переходит на другой VPN/сеть; при возвращении туннеля восстанавливается автоматически.

Те же операции поддерживаются для изменения назначения и удаления правила. Удаление означает явный возврат домена к обычной маршрутизации системы с предупреждением о результате.

## 3. UI и взаимодействие

### FR-UI-01. Окно настроек

Добавить стандартное окно настроек GNOME Shell Extension через `prefs.js`, собранное из TypeScript (`src/prefs.ts` или эквивалент), на GTK4/libadwaita. Оно запускается отдельно от процесса GNOME Shell; UI-логика должна быть асинхронной.

Раздел **Site Routing** включает:

- поле URL/FQDN;
- список подключений с типом и состоянием;
- кнопку «Добавить»;
- список правил: домен, целевое подключение, состояние, количество отслеживаемых IPv4/IPv6, последнее обновление;
- действия «Изменить», «Удалить», «Проверить»;
- сообщение о том, что правки системной маршрутизации требуют подтверждения Polkit;
- понятные ошибки DNS, недоступности интерфейса, конфликта IP и применения маршрутов.

### FR-UI-02. Статусы

Различать как минимум:

- `active` — целевой туннель подтверждён, маршруты применены;
- `blocked-offline` — целевой VPN/физический канал недоступен, защита активна;
- `resolving` — обновление DNS;
- `dns-error` — адреса определить не удалось; известные адреса продолжают защищаться;
- `conflict` — адрес невозможно однозначно назначить разным подключениям;
- `apply-error` — не удалось безопасно применить изменения;
- `provider-missing` — профиль удалён или драйвер недоступен, защита сохраняется для известных адресов.

### FR-UI-03. Ввод

Принимать точные доменные имена и HTTP(S)-URL. Удалять схему, порт, путь, query/fragment; явно показывать, что правило применяется ко **всему хосту**. Нормализовать регистр и интернационализированные имена в каноническое представление IDNA. Валидировать длину, структуру и запрещённые символы до передачи привилегированному процессу. Не принимать wildcard, диапазоны IP и произвольные shell-аргументы в v1.

## 4. Обнаружение подключений

### FR-VPN-01. Провайдеры

- **NetworkManager:** получать сохранённые VPN-профили и активные соединения через D-Bus/libnm; идентифицировать по UUID, а не по изменяемому имени или `tunN`.
- **AdGuard:** использовать существующий `adguardvpn-gnome-ctl`/защищённую службу для определения состояния и соответствующего фактического туннеля; фиксированный внутренний ID `adguardvpn-gnome`.
- **Direct:** определять физический интерфейс и шлюз по фактическому состоянию сети, не считать автоматически, что `main` означает обход всех VPN.

Сохранённый, но отключённый профиль должен отображаться как доступный для назначения, но **неактивный**. Его выбор не запускает VPN. При переименовании профиля правила продолжают работать. При удалении профиля назначенные ему адреса остаются заблокированными до явной смены назначения.

### FR-VPN-02. Проверка доступности

Недостаточно `NetworkManager activated`: необходимо подтверждать фактический интерфейс, IP-конфигурацию и возможность построить маршрут. Отсутствие туннеля при формально активном профиле считается `blocked-offline`. Не использовать постоянные имена `tun0`/`tun1`.

## 5. Движок маршрутизации и fail-closed

### FR-RT-01. Разделение управления

Создать системный компонент маршрутизации, независимый от жизненного цикла окна настроек и GNOME Shell. Его полномочия ограничены правилами Site Routing. Существующий контроллер AdGuard остаётся специализированным на подключении/отключении VPN.

Использовать выделенные таблицы policy routing для управляемых направлений и отдельный слой блокировки (`unreachable` или эквивалент). Приоритеты должны быть выше правил, отправляющих общий трафик в AdGuard, но **выбираться после проверки фактических системных `ip rule`**, без жёсткой зависимости от таблицы `880` или приоритетов конкретной установки.

### FR-RT-02. Порядок безопасного применения

1. Принять и проверить новое правило.
2. Разрешить домен в A/AAAA.
3. Проверить конфликты адресов/таблиц, существующие правила и доступность провайдера.
4. **Прежде чем разрешать маршрут, установить блокирующую защиту** для всех известных адресов.
5. Добавить рабочие маршруты в таблицу выбранного подключения только при подтверждённом туннеле.
6. Проверить получившееся решение для каждого адреса через системное разрешение маршрута.
7. Атомарно зафиксировать состояние; при ошибке сохранить/восстановить безопасную блокировку.

При пропадании VPN рабочие маршруты удаляются или теряют силу, а блокирующая защита продолжает действовать. Если после исчезновения интерфейса ядро автоматически удаляет связанный маршрут, проверка не должна допустить fallback на другие таблицы.

### FR-RT-03. Отдельные назначения

- **NetworkManager VPN:** маршрут через фактический туннель выбранного UUID.
- **AdGuard:** маршрут через защищённый AdGuard TUN, с учётом его собственного AUTO-routing.
- **Direct:** явно вычисленный физический путь в обход VPN, если он доступен.
- **Неизвестный домен:** маршрутизация системы не изменяется.

### FR-RT-04. Конфликты и совместимость

Если один IP принадлежит управляемым доменам с разными назначениями, **не выбирать победителя по приоритету автоматически**. Пометить правила как конфликтные, блокировать затронутые адреса, предложить пользователю изменить назначения. До применения проверять пересечения с существующими политиками маршрутизации. Не менять маршруты и профили, которыми менеджер не владеет, без подтверждённой миграции.

### FR-RT-05. Перезагрузка и сбои службы

Хранить известные адреса и намерение блокировки независимо от состояния динамического туннеля. Служба должна запускаться при старте системы, восстанавливать защиту до предоставления управляемым адресам обычного выхода в сеть и автоматически перезапускаться при сбоях. Защиту раннего старта проверить экспериментально; если требуемое окно без утечки не достигается одним systemd-unit, добавить постоянные ранние firewall-правила либо зафиксировать ограничение и не объявлять критерий выполненным.

## 6. DNS и жизненный цикл правил

### FR-DNS-01. Разрешение и обновление

- Хранить **FQDN**, а не только IP.
- Разрешать все применимые A и AAAA, следовать обычной цепочке CNAME.
- Обновлять по DNS TTL и на событиях изменения сети/провайдера.
- Учитывать DNS выбранного VPN, если он настроен и доступен; ошибки внутреннего DNS не маскировать молчаливым переключением целевого трафика.
- Не удалять защиту для последнего известного адреса одновременно с потерей DNS; обновлять набор адресов по безопасной последовательности.
- Ограничивать частоту запросов и размер списков; ошибки показывать пользователю.

**Граница v1:** приложения с собственным DoH/DoT и IP, не видимые системному DNS-трекеру, не покрываются полной гарантией блокировки. Само содержимое DNS-запросов может идти через действующий системный резолвер; конфиденциальность DNS относительно выбранного VPN не гарантируется отдельно и должна быть описана в документации.

### FR-DNS-02. IPv6

Если домен имеет AAAA-записи, система должна либо применять IPv6-маршрутизацию и защиту наравне с IPv4, либо **отклонять применение правила с явной ошибкой**. Недопустимо показывать статус `active`, если IPv6 может незаметно обойти выбранное подключение.

### FR-LIFE-01. События

Пересогласовывать состояние при:

- подключении, отключении, переподключении и смене IP VPN;
- появлении/исчезновении реального туннеля;
- перезапуске AdGuard и NetworkManager;
- смене сети Wi-Fi/ethernet/шлюза;
- смене DNS или TTL;
- переименовании/удалении NM-профиля;
- запуске системы и рестарте менеджера.

Использовать события NetworkManager/systemd и ограниченный периодический механизм восстановления на случай пропущенных сигналов. Операции должны быть идемпотентными.

## 7. Безопасность и разрешения

### SEC-01. Разделение привилегий

Сохранить действующий безопасный дизайн проекта: защищённая проверенная копия AdGuard CLI, отдельный root-профиль, запрет выполнения пользовательских файлов под root, узкий набор разрешённых команд, отдельные действующие правила Polkit для подключения/отключения.

Для Site Routing создать **отдельную Polkit-операцию** добавления/изменения/удаления правил, требующую интерактивного подтверждения авторизованного локального пользователя/администратора. Чтение собственных правил и состояния может выполняться без дополнительного пароля при проверке прав доступа. Автоматическая переустановка **уже подтверждённых** правил после сетевых событий не должна повторно требовать пароль.

### SEC-02. Валидация

Системный API должен принимать только структурированные операции вида `list-providers`, `list-rules`, `add-rule`, `update-rule`, `remove-rule`, `diagnose-rule`; произвольные shell-команды, скрипты, исполняемые пути, таблицы/интерфейсы от клиента не принимаются. UUID и тип провайдера проверяются по фактическому реестру. Все системные вызовы используют фиксированные абсолютные пути, строгий список аргументов, без `shell=True`.

Сохранённые правила и состояние — root-owned, с безопасными правами, блокировкой конкурентных изменений, версионированием формата и атомарной записью. Не логировать VPN-токены, пароли, ключи или полные частные диагностические данные. В публичных исходниках и тестах использовать только фиктивные домены и адреса.

### SEC-03. AdGuard-профиль

Когда требуется синхронизировать site-exclusions, использовать **только** защищённый профиль `/var/lib/adguardvpn-gnome`, а не обычный пользовательский профиль. Служба должна отслеживать, какие исключения созданы ей самой, не удалять вручную созданные пользователем исключения и не полагаться на site-exclusions как на единственную гарантию нужного маршрута. Изменение режима AdGuard или временный перезапуск допускается только с явной обработкой состояния и ошибок.

## 8. Модель хранения

Рекомендуемый формат состояния (иллюстративный, без персональных данных):

```json
{
  "schema_version": 1,
  "rules": [
    {
      "id": "c48848f4-6b11-40c8-a2f0-e248653bdac4",
      "domain": "packages.corp.example",
      "target": {
        "kind": "networkmanager",
        "id": "00000000-0000-4000-8000-000000000001"
      },
      "fallback": "block",
      "enabled": true
    }
  ]
}
```

Предлагаемое размещение: `/var/lib/adguardvpn-gnome/site-routing/`, доступное только привилегированному backend. В отдельном производном состоянии хранить последнюю известную карту A/AAAA, идентификаторы собственных установленных системных объектов и версии применённой конфигурации. Не делать производные IP постоянным идентификатором правила.

## 9. Миграция и откат

На компьютерах с ранее настроенным split-tunnel уже могут существовать ручные `/32`-маршруты и адресные `ip rule` в NetworkManager. Автоматически удалять их **запрещено**.

План миграции:

1. Обнаружить возможные пересечения и представить пользователю **точный diff** изменений без раскрытия секретов.
2. Сохранить проверяемую резервную копию затрагиваемых NM-настроек.
3. По подтверждению Polkit установить защиту новых правил.
4. Применить новую маршрутизацию и проверить её при обоих VPN.
5. По отдельному подтверждению удалить **только точно сопоставленные** прежние маршруты/правила.
6. Проверить подключение, отключение и повторное подключение каждого VPN.

При неудаче оставить безопасное состояние и предложить откат. Удаление дополнения должно удалять только ресурсы, которыми оно владеет, и явно сообщать, если осталась защитная блокировка. Не допускать бесшумного восстановления потенциально небезопасного fallback.

## 10. Требования к качеству

- Не блокировать GNOME Shell синхронными DNS, сетевыми или привилегированными вызовами.
- Не изменять сетевую конфигурацию при пустом списке правил.
- Применять и очищать системные объекты идемпотентно.
- Сохранять рабочий механизм подключения AdGuard и текущую защиту Polkit.
- Предусмотреть диагностику без вывода учётных данных и приватных URL-путей.
- Не завязывать правила на названия туннелей, численные приоритеты/таблицы конкретного компьютера или отображаемые имена профилей.
- Проверять операции в изолированных Linux network namespaces; не использовать реальную корпоративную сеть в CI.
- Сохранять действующие требования репозитория к покрытию TypeScript- и Python-тестами.
- Поддерживать документированный uninstall/rollback и обновить `README.md`, `extension/README.md`, `docs/privileged-helper.md`.

## 11. Критерии приёмки

| ID | Сценарий | Результат |
| --- | --- | --- |
| AC-01 | Создать точное FQDN → VPN из окна | Правило сохранено после подтверждения Polkit, без команд в терминале |
| AC-02 | Подключение доступно | Все известные A/AAAA направлены через выбранный интерфейс; в UI `active` |
| AC-03 | Целевой VPN отключился | Для известных адресов срабатывает блокировка, не другой VPN/Wi-Fi |
| AC-04 | NM показывает `activated`, но туннеля нет | Статус `blocked-offline`, fallback не происходит |
| AC-05 | VPN переподключён как `tun2` вместо `tun0` | Привязка по UUID сохранена; маршруты восстановлены |
| AC-06 | Переподключён AdGuard в TUN/AUTO | Сохранённые назначения не изменились, конфликтов таблиц нет |
| AC-07 | DNS изменил IP / вернул несколько IP | Набор известных маршрутов обновлён, защита сохраняется во время перехода |
| AC-08 | Два домена имеют один IP и разные назначения | Выведен конфликт, неверный маршрут не применяется |
| AC-09 | Добавлен `direct` | Указан физический путь в обход активных VPN, если доступен |
| AC-10 | Удалён профиль NetworkManager | Управляемые адреса не переходят на системный default; UI сообщает об ошибке |
| AC-11 | Перезапущены NM, служба, затем Fedora | Правила и известные блокировки восстановлены; безопасность раннего старта проверена |
| AC-12 | Правило удалено пользователем | Удалены только связанные собственные маршруты/блокировки; остальная сеть неизменна |
| AC-13 | Нет правил | Текущее поведение системы и AdGuard не меняется |
| AC-14 | Пробуют wildcard, командную инъекцию, неизвестный UUID | Действие отклонено до привилегированного системного вызова |
| AC-15 | Непривилегированный запрос на изменение | Появляется штатное подтверждение Polkit, обхода нет |
| AC-16 | Изменение DNS или ошибка применения | UI показывает фактический статус; не отображает ложное «активно» |
| AC-17 | Ручные NM-правила уже существуют | Обнаружение и миграция без самовольного удаления |
| AC-18 | Конфигурация IPv6 не может быть защищена | Правило не получает ложный статус `active`; применение отклонено безопасно |

**Условие готовности релиза:** воспроизвести и задокументировать все AC на стенде, отдельно подтвердить критические AC-03, AC-04, AC-06, AC-11 на реальной Fedora. Не объявлять функцию абсолютной защитой от любых DNS/IP-утечек.

## 12. Декомпозиция разработки

1. **PR-1: Контракты и модели.** Типы `RoutingRule`, `VpnProvider`, нормализация FQDN, хранение, схемы состояния, unit-тесты.
2. **PR-2: Обнаружение VPN.** Адаптер NetworkManager, адаптер AdGuard, `direct`, определения состояния фактических интерфейсов, тесты на переименование/исчезновение.
3. **PR-3: Привилегированный route backend.** Политика Polkit с подтверждением, fail-closed для известных IP, выделенные таблицы, проверка конфликтов, тесты в network namespaces.
4. **PR-4: UI настроек.** Страница GTK4/libadwaita, списки, редактор, ошибки, интеграция с backend и упаковка в extension ZIP.
5. **PR-5: DNS lifecycle.** A/AAAA, TTL, сетевые события, безопасное обновление, интеграция с защищённым профилем AdGuard.
6. **PR-6: Миграция и релиз.** Дифф, резервная копия, откат, документация, полный регресс, Fedora smoke-тесты.

Изменения выполнять в отдельной ветке, не менять работающую локальную VPN-конфигурацию до готовности и тестирования соответствующего PR. Не коммитить в публичный репозиторий реальные корпоративные адреса и настройки.

## 13. Решения, отложенные за пределы v1

- Суффиксные маски и wildcard `*.example.com`.
- Автоматическое определение «сайт не открывается» и предложение VPN.
- Автоматическое подключение выбранного VPN при посещении сайта.
- Поддержка произвольных автономных VPN-клиентов вне NetworkManager/AdGuard.
- Маршрутизация HTTP-путей, отдельных вкладок и отдельных браузерных профилей.
- Прозрачный прокси для различения разных FQDN на одном IP.
- Гарантии для приложений с собственным DoH и для адресов, не известных DNS-трекеру.
